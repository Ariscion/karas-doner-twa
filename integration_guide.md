# Руководство по интеграции: Клиентское TWA + Бэкенд + Админка Кассира

В данном документе описана архитектура для следующего этапа разработки: связывание клиентского Telegram Web App с базой данных и отдельным приложением кассира (админ-панелью).

---

## 1. Безопасность и Верификация Telegram (TWA)

Перед отправкой любых данных в базу, бэкенд должен убедиться, что запрос подлинный и отправлен именно из Telegram.

1. **Клиентская сторона**:
   Telegram Web App SDK предоставляет строку `window.Telegram.WebApp.initData`, содержащую параметры пользователя, дату создания сессии и хэш подписи:
   ```javascript
   const initData = window.Telegram.WebApp.initData;
   // Данная строка отправляется в заголовке Authorization при каждом запросе
   ```

2. **Проверка на Бэкенде (Node.js/Python/Go)**:
   - Бэкенд получает строку `initData`.
   - Разбирает параметры в Map, сортирует их по алфавиту ключей (кроме параметра `hash`).
   - Соединяет их в формате `key=value` через символ новой строки `\n`.
   - Создает секретный ключ: HMAC-SHA256 от токена вашего Telegram-бота с ключом `"WebAppData"`.
   - Вычисляет HMAC-SHA256 подпись от собранной строки параметров с использованием секретного ключа.
   - Сравнивает вычисленный хэш с хэшем из `initData`. Если они совпадают, данные подлинные.

## 2. Архитектура Базы Данных (СУБД)

Для хранения данных рекомендуется использовать реляционную СУБД (**PostgreSQL** или **MySQL**) для удобного ведения смен и финансовых отчетов.

### Схема таблиц (Пример)

#### Таблица `orders` (Заказы)
| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | SERIAL (PK) | Внутренний ID заказа |
| `order_number` | VARCHAR (Unique) | Номер для клиента (например, `#KD-4829`) |
| `telegram_user_id` | BIGINT | ID пользователя в Telegram |
| `client_name` | VARCHAR | Имя получателя |
| `client_phone` | VARCHAR | Номер телефона для связи |
| `kaspi_phone` | VARCHAR | Номер телефона для Kaspi Pay |
| `delivery_address`| TEXT | Адрес доставки |
| `status` | VARCHAR | Текущий статус заказа |
| `shipping_cost` | INT | Стоимость доставки (500 ₸) |
| `total_amount` | INT | Итоговая сумма заказа (с доставкой) |
| `shift_id` | INT (FK) | Ссылка на текущую кассовую смену |
| `created_at` | TIMESTAMP | Дата и время создания |
| `updated_at` | TIMESTAMP | Дата изменения статуса |

#### Таблица `order_items` (Состав заказа)
| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | SERIAL (PK) | ID записи |
| `order_id` | INT (FK) | Ссылка на заказ |
| `item_id` | VARCHAR | ID товара (например, `doner_classic`) |
| `name` | VARCHAR | Название товара |
| `selected_option` | VARCHAR | Выбранный размер/объем (например, `мега`) |
| `price` | INT | Цена за единицу на момент заказа |
| `quantity` | INT | Количество |

#### Таблица `shifts` (Кассовые Смены)
| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | SERIAL (PK) | ID смены |
| `cashier_id` | INT | ID кассира, открывшего смену |
| `opened_at` | TIMESTAMP | Время открытия смены |
| `closed_at` | TIMESTAMP | Время закрытия смены |
| `status` | VARCHAR | `open` / `closed` |

## 3. REST API Эндпоинты

### Для клиентского приложения:
* `POST /api/orders` — Создание нового заказа (Клиент отправляет корзину и контакты). В ответ получает сгенерированный `#KD-XXXX`.
* `GET /api/orders/active` — Получение данных об активном заказе при перезапуске веб-приложения.

### Для админ-панели кассира:
* `GET /api/admin/orders?status=active` — Получение списка всех активных заказов.
* `GET /api/admin/shifts` — Просмотр отчетов по сменам.
* `POST /api/admin/shifts/open` / `/close` — Открытие/закрытие смены кассира.
* `PUT /api/admin/orders/:id/status` — Изменение статуса заказа (кассир переводит на следующий этап).
* `PUT /api/admin/orders/:id/items` — Редактирование состава заказа кассиром (изменение количеств, цен или удаление блюд).

## 4. Обновление статусов в реальном времени (Real-Time)

Поскольку клиентское приложение должно мгновенно реагировать на действия кассира в админке (выставление счета, начало готовки, передача курьеру), необходимо организовать push-уведомления:

### Вариант А: Server-Sent Events (SSE) — Рекомендуемый
Бэкенд держит открытым HTTP-соединение с клиентом. Когда кассир в админке меняет статус заказа, бэкенд шлет текстовое событие в поток клиента.
* **Плюсы**: Работает по стандартному HTTP, встроенная авто-поддержка переподключения в браузерах, минимальные затраты ресурсов.
* **Минусы**: Односторонний (только от сервера к клиенту, но клиенту и нужно только слушать).

### Вариант Б: WebSockets
Полнодуплексный протокол связи. Клиент и сервер обмениваются сообщениями по постоянному TCP-каналу.
* **Плюсы**: Мгновенный двусторонний обмен данными.
* **Минусы**: Сложнее в настройке (нужно обрабатывать пинги/понги для удержания соединения).
